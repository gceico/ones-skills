# System Organizer

Make an existing agent system easier to understand and maintain while preserving its useful behavior. One maintained home per decision or procedure; load only what the task needs. Organize for the user's actual work and volume, not an imagined enterprise.

## 1. Establish the job and authority

Read the conversation before interviewing. Extract the requested outcome, approved direction, operational source of truth, platform support, independent dependencies and authorization. Separate durable rules from temporary choices and superseded instructions. Later explicit corrections win over earlier proposals.

Distinguish a request to review/propose from a request to implement. If the user approved a concrete reorganization, carry it through without asking permission again for every local move. If the owner of strategy or unique data is genuinely unclear, ask one focused question after doing the useful read-only work.

When extracting a reusable method, use [the placement rules](references/placement-rules.md) to separate general principles from the originating team's choices. Do not turn its CRM vendor, folder names, five departments or naming style into universal requirements.

## 2. Inspect the actual system

Read repository instructions, manifests, entry points, relevant source and the affected references. Record existing changes before editing. Code and configuration establish what exists; prose can be stale. Respect working cross-platform support rather than rebuilding it.

Inventory the material that affects the task and its consumers. Search Markdown links, literal paths, command routes, skill descriptions, manifests, scripts and runtime loaders. A file without an inbound link may still be a user entry point or required asset; a referenced file may still be obsolete. Do not classify by filename alone.

For each disputed item, identify purpose, authority, readers, whether it is reusable guidance or a live record, and its likely destination. For competing strategies, use the direction the user approved. Preserve useful tactics only after reconciling audience, offers, language, cadence and data ownership. Do not silently choose whichever document is newest.

## 3. Propose the smallest coherent structure

Apply [placement rules](references/placement-rules.md). Produce a compact keep/move/merge/remove table with current path, destination and reason, plus only the consequential behavior changes. Do not create a new permanent inventory database or a folder for every concept.

Prefer understandable capability names. Broad skills may group related work into studios; focused actions may expose command-like entry points. Size alone does not decide the shape. Use the host's existing portable mechanism and keep one procedure behind all entry points.

Resolve contradictions rather than relocating them. Separate approved messaging from finished page copy, blank templates from client deliverables, measurement rules from dated reports, and source evidence from instructions. Explain any planned loss of capability or unique material.

For review-only work, deliver the proposal and stop. For authorized implementation, continue with [the migration checks](references/migration-checks.md).

## 4. Migrate without losing behavior

Preserve originals or establish recoverability before removing unique or uncommitted material. A temporary backup is a recovery aid, not a completed transfer to the operational system. Do not delete data simply because it belongs elsewhere. Keep uncertain records in place or prepare an explicit handoff when no durable destination is authorized.

Move one maintained procedure, then update all its consumers. Keep original examples intact apart from necessary reference repairs; do not rewrite captured facts to fit new rules. Preserve useful modes such as check-only, lightweight editing, approval before sending and output-format contracts.

Keep independent plugins independent. Read their supported outputs or invoke their workflows; do not copy their engine, schemas or state into the reorganized system. Folder cleanup does not authorize syncing, publishing, migrating remote data, changing access or releasing a plugin.

Keep operational inputs and outputs in the user's chosen system of record. Inspect only what the task needs. Return a ready-to-use handoff if access is missing; do not create a replacement inbox, CRM, CMS or analytics archive by default.

## 5. Verify and deliver

Check actual local links, inline paths, resource identifiers, command routes and manifest references. Distinguish placeholders, historical source text and pre-existing defects from broken live dependencies. Validate changed frontmatter and packaging with available tools; do not add application build gates to a documentation plugin.

Exercise representative workflows where behavior or routing changed. At minimum, check a broad task, a focused shortcut and a missing-tool or ambiguous-data case where relevant. Use an isolated workspace for executable trials. A schema check does not establish behavioral correctness, and a local trial does not establish installation in every supported host.

Finish with what changed, where the maintained rules now live, checks actually performed, and any preserved material or unresolved transfer. State whether changes are local, installed or published. Do not claim a Notion/database migration, release or cross-platform test that did not happen.

## Ongoing maintenance

When adding material, identify its owner and current callers first. Update the canonical source, then affected references. Promote repeated cross-workflow guidance only when it is actually shared. Retire stale instructions and repair their consumers in the same change. Keep historical observations from becoming mandatory current behavior.

Keep the operating guide short: where things belong, what is authoritative, how outputs are handled and how changes are verified. Do not make a second operating system that repeats every skill. Revisit structure when real friction appears, not on an invented recurring schedule.

## Runtime

Use the host's available file/resource, search and editing tools. Relative links resolve from the containing resource; resolve bundled content inside the installed package, not the user's current directory or an author's machine path. When no filesystem or write access is available, review supplied material and return a concrete migration plan instead of pretending to apply it. Optional delegation or external connectors are not prerequisites.
